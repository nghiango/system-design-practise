# System Design Practise — Foundation Design

Status: draft for approval · Date: 2026-11-18

## 1. Intent

Build six system-design topics as **complete, working Java reference solutions**
that can be studied, deployed and load-tested on the local kind cluster
(`kind-hyperscale-k8s`):

| # | Topic | Focus | Level |
|---|---|---|---|
| 1 | URL Shortener | capacity estimation, sharding, caching, ID generation | Foundational |
| 2 | Flash Sale | inventory consistency, high concurrency, overselling prevention | Intermediate–Advanced |
| 3 | Notification System | high-volume queues, retries, rate limits, delivery guarantees | Intermediate |
| 4 | Ticket Booking | seat locking, reservation expiry, payment, race conditions | Advanced |
| 5 | Banking Money Transfer | ACID, idempotency, ledger, distributed transactions, recovery | Advanced |
| 6 | Real-Time Auction | concurrent bids, ordering, WebSocket broadcast, consistency | Advanced |

The table order is the build order: foundation + URL Shortener first (cheapest way
to prove the whole build → GitOps → cluster pipeline), then one topic at a time.

**Why:** learning. Each topic must explain *what* was built and *why each technology
was chosen over the alternatives*, and a progress tracker must keep the six topics
from becoming overwhelming.

## 2. Goals, non-goals, anti-goals

Goals
- Each topic is independently deployable and can be switched **on/off with one line
  in Git**.
- It is obvious, everywhere (code, Git, cluster, dashboards), which part belongs to
  which topic.
- Every topic documents requirements, capacity estimate, architecture, technology
  choices with reasons and rejected alternatives, failure scenarios, and recorded
  load-test evidence.
- `PROGRESS.md` shows status and the next step at a glance.

Non-goals
- Per-topic dedicated Kafka/Redis/Postgres (decided: shared infrastructure).
- Production-grade security, multi-cluster, or real payment providers.
- Building all six topics in one go; each later topic gets its own short design
  round before it is built.

Anti-goals (failure even if it "works")
- Topics coupled to each other: no topic calls another topic, or reads another
  topic's database, Kafka topics or Redis keys.
- Breaking or modifying the existing HyperScale Commerce deployment behaviour.
- Docs that state a choice without the reason and the alternative it beat.

## 3. Constraints found in the existing setup

- GitOps repo `hyper-scale-commerce-gitops` has three Argo Applications
  (application / infrastructure / platform), all in namespace `hyperscale`.
- Charts there are **generated by Jenkins** from the `hyper-scale-commerce` repo
  (`local-ci/scripts/release.py` deletes and recreates `charts/<scope>`). Hand edits
  to those charts are overwritten. Topic material must live in a separate path
  that this script never touches.
- Shared infra runs in `hyperscale`: Kafka (3 brokers, KRaft), Patroni/Postgres (3),
  Redis, etcd, Vault + External Secrets (`ClusterSecretStore vault-backend`, policy
  reads `secret/data/hyperscale/*`).
- `hyperscale` has **default-deny NetworkPolicies**; Postgres/Kafka/Redis only accept
  pods labelled `app.kubernetes.io/name: hyperscale-commerce` in that namespace.
- Existing Postgres connection budget comment: ~96 connections already reserved.
- Argo sync policy there: automated, selfHeal, prune disabled.
- Existing project conventions to reuse: Gradle Kotlin DSL, Java 21 toolchain,
  Spring Boot 4.0.0, Spotless + google-java-format, Testcontainers, k6 for load,
  ARM64 images via `docker buildx` to registry `hyperscale-k8s-worker:30500`.

## 4. Approaches considered

Shared vs isolated infra
- **Shared (chosen by user):** topics reuse the existing Kafka/Redis/Postgres,
  isolated by namespace, database, Kafka topic prefix and Redis key prefix. Light
  enough for kind.
- Fully isolated per topic: true independence and per-topic tuning, but ~6× stateful
  pods; too heavy locally.

On/off mechanism
- **One flag per topic + Argo ApplicationSet (chosen by user):** an ApplicationSet
  generates one Argo Application per enabled topic; flipping `enabled` adds/removes
  it, and a cleanup finalizer removes its resources.
- One Argo Application file per topic: simpler, but "off" means deleting a file and
  there is no single readable switchboard.
- Repo per topic: rejected (six pipelines, duplicated build code, no learning gain).

User requirement on top of option 1: **layout must make topic ownership easy to read.**

## 5. Design

### 5.1 Naming convention (the ownership rule)

Every artefact carries the topic slug (`url-shortener`, `flash-sale`,
`notification`, `ticket-booking`, `banking-transfer`, `auction`):

| Artefact | Pattern | Example |
|---|---|---|
| Source folder | `topics/<topic>/` | `topics/flash-sale/` |
| Gradle module | `:<topic>:<service>` | `:flash-sale:inventory-service` |
| Java package | `com.systemdesign.<topicnodash>.<service>` | `com.systemdesign.flashsale.inventory` |
| Container image | `<registry>/system-design/<topic>-<service>:<sha>` | `.../system-design/flash-sale-inventory-service:ab12…` |
| GitOps folder | `topics/<topic>/` | `topics/flash-sale/` |
| Argo Application | `topic-<topic>` | `topic-flash-sale` |
| Namespace | `topic-<topic>` | `topic-flash-sale` |
| Label on every resource | `system-design/topic: <topic>` | `system-design/topic: flash-sale` |
| Postgres database | `<topic_underscored>` | `flash_sale` |
| Kafka topic | `<topic>.<entity>.<event>` | `flash-sale.order.created` |
| Kafka consumer group | `<topic>.<service>` | `flash-sale.order-service` |
| Redis key prefix | `<topic>:` | `flash-sale:stock:{sku}` |
| Policy in `hyperscale` ns | `topic-<topic>-allow-shared-infra` | |
| Logs (Loki) | `{namespace="topic-<topic>"}` | |

### 5.2 Application repo (`system-design-practise`)

```
system-design-practise/
├── README.md                 # what this is, how to run, naming convention
├── PROGRESS.md               # the tracker (5.6)
├── AGENTS.md                 # build/test/verify commands for agents
├── settings.gradle.kts       # includes topics/*/services/*
├── build.gradle.kts
├── gradle/libs.versions.toml # one version catalog for all topics
├── build-logic/              # convention plugin `sd.spring-service`
│                             # (Java 21, Boot, Spotless, test + integrationTest, actuator, OTel)
├── ci/
│   ├── Jenkinsfile
│   └── scripts/              # detect changed topics, build/push images, publish to GitOps
├── scripts/topic.sh          # port-forward | logs | load <topic> <scenario> | status
├── docs/
│   ├── topic-template.md     # the README skeleton every topic copies
│   └── superpowers/specs/    # design docs (this file, then one per topic)
└── topics/
    └── url-shortener/
        ├── README.md         # the topic's main doc (5.5)
        ├── docs/decisions/   # 0001-id-generation.md, 0002-sharding.md, ...
        ├── services/
        │   ├── link-service/      (Gradle module + Dockerfile)
        │   └── ...
        ├── deploy/chart/     # Helm chart source; Jenkins copies it to GitOps
        └── load/             # k6 scenarios
```

Shared Java libraries are **not** created up front. Only the build convention is
shared. A `libs/` module is added only when a second topic actually needs the same
code (for example an idempotency helper), and it is recorded in a decision doc.

### 5.3 GitOps repo additions (`hyper-scale-commerce-gitops`)

Everything for a topic lives in one folder, separate from the Jenkins-owned
`charts/` and `environments/`:

```
hyper-scale-commerce-gitops/
├── argocd/
│   ├── applications.yaml          # unchanged
│   └── topics-applicationset.yaml # NEW: generates topic-<topic> Applications
└── topics/                        # NEW: never touched by the commerce release.py
    ├── README.md                  # switchboard explanation + table of topics
    └── url-shortener/
        ├── topic.yaml             # HUMAN-owned: enabled flag + description
        ├── values-local.yaml      # JENKINS-owned: image tags, revision
        └── chart/                 # JENKINS-owned: copied from app repo
```

`topic.yaml` (the on/off switch):
```yaml
name: url-shortener
enabled: "true"        # set to "false" to switch the topic off
description: Capacity estimation, sharding, caching, ID generation
```

ApplicationSet:
- Git **files** generator over `topics/*/topic.yaml`, with a `selector` that keeps
  only `enabled: "true"`.
- Template: Application `topic-{{name}}`, source path `topics/{{name}}/chart`, value
  file `../values-local.yaml`, destination namespace `topic-{{name}}`, labels
  `system-design/topic: {{name}}`, finalizer
  `resources-finalizer.argocd.argoproj.io`, automated sync with selfHeal and
  **prune enabled** (a topic owns only stateless resources, so pruning is safe and
  keeps "off" clean).
- Applied once with `kubectl apply -f argocd/topics-applicationset.yaml`, the same
  way as the existing `applications.yaml`.

Switching **off**: the Application is deleted → the finalizer removes the
namespace, Deployments and the topic's NetworkPolicies in `hyperscale`. The topic's
database, Kafka topics and Redis keys stay on the shared infra, so data survives.
Switching **on** recreates everything and reuses that data. A per-topic `reset` in
`scripts/topic.sh` (drop DB / delete Kafka topics / delete Redis keys by prefix)
is the explicit way to wipe data, and it asks for confirmation.

Warning (README): deleting the ApplicationSet itself switches off all topics.

### 5.4 What each topic chart contains

- `Namespace topic-<topic>` (owned by the chart, so it is removed on "off").
- Deployments + Services per service, with small resource requests (kind budget).
- NetworkPolicies:
  - in `topic-<topic>`: default-deny, plus allow DNS, allow egress to `hyperscale`
    shared infra and the OTel collector, and allow ingress between the topic's own
    services and from the topic's k6 job.
  - in `hyperscale`: `topic-<topic>-allow-shared-infra`, which allows ingress to
    Postgres 5432, Kafka 9092, Redis 6379 from
    `namespaceSelector: system-design/topic=<topic>`. These policies are only
    added to, so the existing policies are not edited.
- ExternalSecrets (via the existing `ClusterSecretStore vault-backend`) that copy
  the shared Postgres and Redis credentials (`hyperscale/postgres`,
  `hyperscale/redis`) into the topic namespace.
- Argo **PreSync hook Jobs** (idempotent):
  - create database `<topic_underscored>` if missing;
  - create the topic's Kafka topics with `--if-not-exists`, using partitions
    declared in values (replication factor 3, as in the existing cluster).
- Schema is owned by each service via Flyway on startup.
- HPAs only where the topic's design calls for them, with Argo `ignoreDifferences`
  on replicas (as the existing app does).

Access from the laptop: `scripts/topic.sh port-forward <topic>`. No new NodePorts,
and the Jenkins-owned HAProxy ingress is not changed. Load tests run **in the
cluster** as a k6 Job (`scripts/topic.sh load <topic> <scenario>`), so
port-forwarding does not limit throughput.

### 5.5 Per-topic documentation (`docs/topic-template.md`)

Each `topics/<topic>/README.md` has these sections:
1. Problem and requirements: functional, plus non-functional with numbers.
2. Capacity estimation: QPS, storage, bandwidth, and how the local scale-down
   relates to them.
3. API.
4. Data model.
5. Architecture: a Mermaid diagram, plus a step-by-step flow for the main request.
6. The hard problems and how they are solved (for example overselling, and why the
   naive version fails).
7. Technology choices: table *Need | Chosen | Why | Rejected alternatives* → link to
   `docs/decisions/NNNN-*.md` (Context / Options / Decision / Consequences).
8. Failure scenarios and recovery: what happens when Redis, Kafka or a pod dies.
9. Run and verify: commands, the k6 scenarios, and **recorded results** (numbers,
   date, revision).
10. Experiments to try next.

### 5.6 Progress tracking (`PROGRESS.md`)

```
| Topic            | Design | Services | Tests | Chart | Deployed | Load evidence | Docs | Status      |
|------------------|--------|----------|-------|-------|----------|---------------|------|-------------|
| Foundation       |   ✔    |    –     |   ✔   |   ✔   |    ✔     |      –        |  ✔   | done        |
| URL Shortener    |   ✔    |    ◐     |       |       |          |               |      | in progress |
| Flash Sale       |        |          |       |       |          |               |      | not started |
...
Next step: <one line>
```
Under the table, each topic has a short checklist of its concrete tasks, and a
log line (date, what changed) for every completed step. The row is updated as part
of every change, not afterwards.

### 5.7 CI/CD

- A second Jenkins pipeline job polls `system-design-practise` (`ci/Jenkinsfile`).
- Stages: changed-topic detection (diff against the last successful commit; if
  that is unknown, build all) → unit tests → integration tests (optional, as in the
  existing pipeline) → ARM64 image build/push per changed service → publish.
- Publish clones the GitOps repo and, for each changed topic only, replaces
  `topics/<topic>/chart` and rewrites `topics/<topic>/values-local.yaml` with the
  image tags. It runs `helm lint`, then commits
  `Deploy topic <topic> <sha> (linux/arm64)`. It **never writes `topic.yaml`**, and
  never touches `charts/` or `environments/`.

### 5.8 Observability

Services expose `/actuator/prometheus` and send traces to the existing collector
(`otel-collector.hyperscale.svc:9411`). Today Prometheus and Alloy only watch
namespace `hyperscale`. Their config is generated from
`hyper-scale-commerce/local-ci/platform`, so it must be widened to `topic-*`
namespaces there (see Open questions).

### 5.9 First topic: URL Shortener (outline; detailed in its own README)

- Services: `link-service` (create short links; write path), `redirect-service`
  (resolve + 302; hot read path, Redis cache-aside), `analytics-service` (consumes
  `url-shortener.link.clicked` from Kafka and aggregates click counts).
- ID generation: 64-bit Snowflake-style ID → base62 code. The worker ID comes from
  a lease, and the decision doc compares Snowflake, a DB sequence, random-with-retry
  and pre-generated key ranges.
- Sharding: N **logical** shards (one schema per shard inside database
  `url_shortener`), routed by hash of the code. The doc is explicit that every shard
  runs on the same physical Patroni cluster locally, and explains how this maps to
  physical shards.
- Capacity example in the doc: 100M new links/month, 100:1 read:write, 5-year
  retention. The local k6 targets are a scaled-down version of that.

## 6. Success criteria for the foundation + URL Shortener

- `./gradlew build` passes, with unit tests and Testcontainers integration tests.
- `helm lint` and `helm template` pass for the topic chart. The ApplicationSet
  renders only enabled topics.
- With `enabled: "true"`, Argo shows `topic-url-shortener` Healthy. Create +
  redirect work through port-forward, and a k6 run records numbers in the README.
- Flipping to `"false"` removes the Application, the namespace and the
  `hyperscale`-side policies. Flipping back restores the service, and existing
  links still resolve.
- The existing `hyperscale-local*` Applications stay Healthy and unchanged
  throughout.
- `PROGRESS.md` and the topic README are complete for this stage.

## 7. Calls made by the designer (reviewable)

- Java 21, Spring Boot 4.0.0, Gradle Kotlin DSL, Spotless, Testcontainers, k6, to
  match `hyper-scale-commerce`.
- Topics use the **shared** Postgres and Redis credentials (no per-topic DB users).
  This is simpler; the cost is weaker isolation, which is documented as a
  trade-off.
- Prune enabled for topic Applications (unlike the commerce apps) because topics own
  no persistent volumes.
- Laptop access via port-forward; load runs inside the cluster.
- No shared Java library until a second topic needs one.

## 8. Left to the builder

- Exact Postgres superuser name and service names (read from the infrastructure
  chart); per-pod pool sizes inside the remaining connection budget (measure
  `max_connections` first).
- Changed-topic detection details in the Jenkinsfile.
- Resource requests, replica counts, and partition counts per Kafka topic.
